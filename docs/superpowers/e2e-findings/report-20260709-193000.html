Summary

The codebase has a real design system (chassis vs hardware tokens, documented at the top of rack.css) but a long tail of inline-styled re-implementations of it in rack.js. The "ONE status→presentation mapping" comment near statusView shows the developer was aware of mirror-consistency for state, but the visual system has drifted in parallel: the same modal OK button, the same small ghost button, the same bargraph LED cell, and the same modal title are redefined inline 5–10 times each. Empty-state usage is mostly consistent (good), but a few places use raw inline-styled divs instead of the .empty-unit class. Spacing between the page title bar (.page-head) and the units below it is slightly off in the detail page. Nothing is broken or unsafe; this is a clean polish pass.

  • 1 blocker (cancelled status in detail header — see F-2.3)
  • 7 major findings — inline-style extraction, page-head alignment, focus styles, status badge coloring
  • 12 minor findings — copy clarity, missing states, micro-spacing
  • All findings are CSS-primary + 2-3 line JS edits.
  • No backend changes required.

Inline-style drift (8 findings)

The single biggest category. 240+ inline style="..." attributes in rack.js re-implement CSS that already exists. The most repeated offenders are below; each one already has a CSS token, just no class.

F-1.1 Major rack.js lines 361, 450, 480, 1368, 2027, 2069, 2906, 2947, 2986 (and growing)
Amber "OK" / "Confirm" button re-defined inline 9 times.

Each of these lines writes the identical 7-property amber pill (font-family, font-size, font-weight, background, color, border, padding, border-radius, cursor) that .btn--amber in rack.css:448 already provides. New modals keep copying it because the JS author wasn't sure the class covers their case (it does).

Fix: Add a single .btn--amber.btn--sm combo (or define .btn--amber as a small primary variant) and replace the 9 inline-styled button elements with class="btn btn--amber btn--sm". Zero behavior change. This is the highest-leverage fix in the whole audit.

F-1.5 Major rack.js detailTabsHtml() line 1860
Detail-tab "key" pill re-implements the .key class inline.

The tab pill in the transcript detail page writes its own gradient/box-shadow/border/border-radius/box-shadow stack. The CSS class .key (rack.css:305) is the exact same component in a different size — a smaller variant could trivially be .key--sm.

Fix: Add .key--sm { width:110px; height:30px; } and refactor detailTabsHtml() to use class="key key--sm" with .key.active / .key.inactive variants. The "active" vs "inactive" gradient is the same two gradients used in .key and .key:disabled, so this is straightforward.
F-1.6 Major rack.js lines 551, 1162, 1168, 1719; rack.js line 211-214 (bargraph helper)
LED bargraph cells inline-styled per element instead of CSS custom property.

Every "lit" cell writes style="background:;box-shadow:0 0 4px ". The base .bargraph > span already has the off-state styling; only the on-state colors vary, and they're always the three semantic colors (green/amber/red) plus a few job-specific tints.

Fix: Add .bargraph > span.on { background: var(--on-color, var(--led-off)); box-shadow: 0 0 4px var(--on-color, transparent); } and have the helpers set style="--on-color: GREEN" (one property) instead of two. Same approach for ledDot(). Net result: ~30% less inline style string per cell, and consistent cell rendering.
F-1.7 Minor rack.js line 1691 (jobActions) and ~30 small button overrides
"Small button" font-size:12px + padding:6px 12px inline-styled 30+ times.

Bank row actions, queue job actions, detail-page action bar, summary buttons, voice roster buttons — all write the same style="font-size:12px;padding:6px 12px..." on top of .btn.

Fix: Once .btn--sm exists (per F-1.2), this collapses to class="btn btn--sm". The other inline overrides (border-color, font-size:11px, padding:5px 12px, etc.) reduce to the same handful of variants.
F-1.8 Minor rack.js lines 2817-2819 (voice clip play/del), 2835 (add clip), 2900, 2943, 2980 (file pick)
File-pick button re-defined inline 3 times.

Identical pattern: monospace, dashed border, dim label, "Choose an audio file…".

Fix: Add .btn--file-pick class. One place to update copy or style.

F-2.2 Major rack.js line 2394 (renderDetail())
Detail page-head has a style="gap:14px" override that no other page has.

The transcript detail page adds style="gap:14px" to .page-head to make room for the action-button row. Other pages' .page-heads have the default 0 gap (just justify-content: space-between). Result: the detail page title bar visually differs from every other page's title bar.

Fix: Add a .page-head--with-actions { gap: 14px; flex-wrap: wrap; align-items: center; } class and use it on the detail page only. I'd add the class to keep the intent explicit.
F-2.3 Blocker rack.js statusView() line 264; jobStatusView() line 1682; renderDetail() line 2419; bankDetailFields() line 1521
Cancelled status renders inconsistently in the detail header.

Per the project's own log entry (Observation 3, 2026-07-02), a cancelled transcript was shown as red "Failed" in the detail header until that was fixed. The current state: statusView has case 'cancelled': color=AMBER, nixVariant='dim', word='cancelled' (correct), and renderDetail() line 2419 uses sv.color for the status badge (so it correctly renders amber-dim, not red). This was fixed since the 2026-07-02 incident — but I want to flag it as something to verify in the re-test, because the previous fix and any future re-fix both live in the same fragile place (the renderDetail() status badge with no class wrapper).

Fix: Replace the inline style="color:${sv.color}" on the status badge with a class-based approach (e.g. class="status-badge status--${sv.word}" with colors defined in CSS). This makes the cancelled→amber mapping impossible to break with a stray inline style. Verify the same change in the bank row, queue row, and dashboard recents — they all currently use sv.color inline, so they need the same class conversion for the fix to be robust.

Missing states (4 findings)

F-3.1 Major rack.css .btn line 431; .btn:focus-visible missing
Buttons have no focus-visible style — only inputs do.

:focus-visible on body adds the amber outline (rack.css:76) which is good for global focus, but .btn is the only major clickable that doesn't have a more specific focus state. The outline-on-everything global is OK but can feel noisy. A .btn:focus-visible with a tighter outline (1px amber inset, or a 2px box-shadow ring) would feel more like a real button focus.

Fix: Add .btn:focus-visible { outline: none; box-shadow: 0 0 0 2px var(--amber); }. Light, accessible, doesn't fight the global focus rule for non-button controls.
F-3.2 Minor rack.css .btn--amber line 448
Amber button has no hover state.

Regular .btn and .btn--red both have hover styles; .btn--amber doesn't.

Fix: Add .btn--amber:hover { background: #f0b94a; border-color: #f0b94a; } (a slightly brighter amber).
F-3.3 Minor rack.css .inp.error missing
No error state for inputs.

Form validation errors (e.g. "Speaker name required" toast in openEnrollModal) currently surface only as toasts. An .inp.error border (e.g. 1px solid --red) would let the field itself show it, but it's a meaningful behavior change requiring a new pattern. Defer unless we expand scope.

Fix (if pursued): Add .inp.error { border-color: var(--red); } and have modals toggle it for empty-required fields on submit. Not a 1-line fix — needs a small "show field error" helper.
F-3.4 Minor rack.css .rail-foot .row line 192
Rail-foot "Storage" label is 9.5px — borderline at 1440px+, near-illegible at high DPI.

Other small captions are 9.5px or 10.5px; the rail-foot text uses 9.5px with 0.08em letter-spacing in the same monospace as the rail LED labels. On a 1080p display the row "0 / 500 MIN" is readable; on a 4K display with browser zoom, it's nearly too small. Probably fine for now but worth noting.

Fix: Bump to 10.5px to match .t-cap (line 88) and the other rail captions. Lowest priority of the spacing findings.

Copy / clarity (3 findings)

F-4.1 Minor index.html line 30
Passcode field has no placeholder (Operator does).

By design — passcode fields shouldn't show placeholder for security. So this is technically consistent with the rest of the web. Not a bug. Mention only because a less-experienced user might wonder if the field is broken. Could add a single aria-label="passcode" for accessibility (it already has autocomplete="current-password" which is the more important thing).

Fix: None needed. (Optional: aria-label="passcode" on the input.)
F-4.2 Minor index.html line 36-38
Auth LED is a tiny dark dot, hard to read state.

The id="auth-led" dot above "Power on" is a bare led-dot with no initial color (so it looks dark). On successful login it becomes green (rack.js:511-512), but the success state flashes for <1s before the page transition hides the login. The user never sees "you're in" feedback on the LED itself.

Fix: Two options: (a) Add a subtle "standby" amber glow to the LED by default in CSS (e.g. #auth-led { background: var(--amber); box-shadow: 0 0 5px var(--amber); opacity: 0.5; }) so the user knows it's interactive; (b) leave as-is and add a CSS animation for the success state. I'd do (a) — it's a 2-line CSS change and signals "the system is on, waiting".
F-4.3 Minor rack.js line 538
"processing X-min recording — no section data on this run" reads as an error.

The status word "working" in the dashboard recents is followed by meta text that begins "processing X-min recording — no section data on this run" (line 538). This is honest copy, but to a user it sounds like something failed. The state is actually "running but the model is producing a single block, not chunks" — a working condition.

Fix: Rephrase to something more reassuring, e.g. 'transcribing a ' + X + '-min recording — running as one block'. Subjective copy fix; the exact wording is a judgment call.

Mirror consistency (2 findings)

F-5.1 Major index.html line 96; rack.js line 1543-1544 (Tape library status); rack.js line 1753 (Queue status)
Page status colors are inline-styled; would break if the .page-status class was restyled.

Each .page-status in the bank, queue, and dashboard has an inline style="color:${GREEN}" or style="color:${active ? AMBER : GREEN}". Per the "mirror consistency" principle the user's own log flagged, a page status color set inline in one place but not another (or set in a class but overridden inline) will silently drift.

Fix: Define .page-status--ok { color: var(--green); } and .page-status--busy { color: var(--amber); } and have the JS use those classes instead of inline color. Cheap, removes a class of bug.

What I checked but did NOT find problems with

  • Status mapping consistency. Both statusView (for transcripts) and jobStatusView (for queue jobs) handle completed/failed/partial/cancelled/processing/running/waiting/queued the same way. Cancelled is consistently AMBER + dim. Good.
  • Empty states for bank/queue/voices/dashboard. All use .empty-unit.
  • Empty states for correction/summary "not yet". Both use .empty-unit.
  • Accessibility baseline. Global :focus-visible outline exists. ARIA roles are present (modal has role="dialog" aria-modal="true"). Audio controls have aria-hidden for decorative buttons. Some inputs lack explicit aria-label (e.g. the LED dots in the rail) but they have title attributes as a fallback.
  • The login screenshot (1440×900) renders cleanly: industrial panel, amber standby LED, monospaced font hierarchy, "POWER ON" key pill clearly the primary action. The 4 corner screws are a nice metaphor touch.
